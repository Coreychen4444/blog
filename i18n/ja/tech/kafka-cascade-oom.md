この OOM は私自身が引き起こしたものです。ロジックの修正は正しかったのですが、大きなネットワークのデータで検証していませんでした。リリース後、大規模テナントの最上位パートナーが設定を変えるたびに、カスケード処理のコンシューマーの Pod がメモリを使い切り、強制終了され、再起動し、また使い切りました。

この記事では、それがどう起きたか、どう直したか、そして直した後に何が残ったかを記録します。

## 背景：不変条件を守らなければならない木

プラットフォーム上のパートナーネットワークは木構造で、通常モードでは最大10階層です。各ノードは、商品カテゴリごとの分配ルールと、通貨ごとの取引上限を持っています。

システムには守るべき不変条件が一つあります。**下位の値は直属の上位の値を超えてはならない**、というものです。上位が設定を変えると、サービスがカスケードイベントを発行し、Kafka コンシューマーが下位全体をあらためて切り詰めます。

このコンシューマーの最初の版は同僚が書いたものです。バッチ処理はしていましたが、すべての下位を「変更された本人」と比較していました。その後、要件が**それぞれの直属の上位の新しい値で切り詰める**ように変わり、その修正を私が担当しました。各下位の直属の上位の新しい値を得るために、もともと1バッチ200件だったループを、下位全員とその上位の設定を一度に読み込む形に書き換えました。

ロジックは正しかったのですが、メモリには上限がありませんでした。

## 症状：1件のメッセージがパーティションを止める

リリース後、私はこのコンシューマーを見張り続けていました。

- 大規模テナントの最上位パートナーがルールを変えるたびに、コンシューマーの Pod がメモリを使い切り、OOMKill されて再起動する。
- 強制終了の時点でそのメッセージの offset はまだコミットされていないため、再起動後に再配信され、また OOM になり、Pod が再起動ループに入る。
- 同じパーティションの後続イベントがすべて詰まる。
- 小規模テナントではまったく問題がない。

最後の点が決め手でした。大きなネットワークでだけ失敗するということは、ロジックの誤りではなく、データ量に関係する問題だということです。

## 原因の特定：ネットワーク規模に比例する読み込み

1. **範囲を絞る**。カスケードイベントでだけ起き、大きなネットワークでだけ起き、時期は私の変更の直後でした。
2. **メモリを見積もる**。設定の行数 = 下位の人数 × 商品カテゴリ数 × 種別数で、各行には通貨ごとの JSON も付きます。一度に読み込むということは、サブツリー全体の設定をメモリ上にデシリアライズすることです。メモリはネットワーク規模に比例して増え、上限がありません。
3. **確認する**。diff を見ると、構造上の変更は「バッチ処理」を「全件読み込み」にしたことだけでした。

## 修正：先に依存関係を見つけ、それからバッチに分ける

全件読み込みに変えたのは、バッチに分けると正しさが崩れると心配したからです。下位は直属の上位の**新しい**値と比較しなければならず、もし下の階層を先に計算すると、上位の古い値を読んでしまいます。

しかし依存関係を図にすると、答えははっきりしました。**階層と階層の間には依存があるが、同じ階層の中にはない**。順番に処理する必要があるのは階層の間だけで、階層の中は自由にバッチに分けられます。

```text
上位 P が設定を変更 → DB に書き込み → カスケードイベントを発行 {旧値, 新値, オプション}
                                │
[カスケードコンシューマー]  失敗時 → 専用の retry topic（回数上限あり、間隔は漸増）→ デッドレター
  1. P の下位全員を取得（id と階層のみ）
  2. 階層ごとにグループ化し、上から順に1階層ずつ処理：
       各階層を200件ずつのバッチに分割
         → このバッチの直属の上位の（新しい）設定だけを読み込む
         → 各下位を直属の上位の新しい値で切り詰める → DB に書き込み
         → バッチ間で 50 ms 待つ
  3. 影響を受けたユーザーのキャッシュを削除
```

中心となるループはおおよそ次のとおりです（説明用のコードで、元のコードではありません）。

```go
for depth := 1; depth <= maxDepth; depth++ { // 階層間は順番に：上の階層を書き終えてから、次の階層が新しい値を読める
	ids := idsByDepth[depth]
	for start := 0; start < len(ids); start += batchSize {
		batch := ids[start:min(start+batchSize, len(ids))]

		// このバッチの直属の上位だけを読み込むので、メモリは batchSize だけで決まる
		parents, err := store.LoadParentSettings(ctx, batch)
		if err != nil {
			return err
		}
		updated := clampToParents(batch, parents) // 下位は直属の上位を超えられない
		if err := store.SaveSettings(ctx, updated); err != nil {
			return err
		}
		time.Sleep(pause) // バックグラウンド処理なので、DB をオンラインのリクエストに譲る
	}
}
```

いくつかのトレードオフです。

| 選択 | 理由 | 採らなかった案 |
|---|---|---|
| 階層ごとに上から下へ | 階層間には依存があり、階層内にはない | 木全体をトポロジカルソートしてメモリ上で処理する。これこそ OOM を起こしたやり方 |
| バッチごとに直属の上位だけを読み込む | 階層の幅が広いと、上位の階層全体も大きくなる | 上位の階層全体を読み込む（最初の修正はこれで、後でさらに絞り込んだ） |
| バッチ内は逐次、バッチ間で 50 ms 待つ | カスケードはバックグラウンド処理で、リアルタイム性は求められない | 階層内の並行処理。MySQL への負荷が何倍にもなる |
| ルールは Go 側に置く | 切り詰めには通貨ごとの JSON と複数の種別が関わる | 再帰 CTE の SQL 1本で計算する。これらのルールを表現できない |

修正は2段階でリリースしました。まず階層ごとのバッチ処理にして OOM を解消し、その後「上位の階層全体を読む」を「このバッチの直属の上位だけを読む」に絞り込みました。

検証の方法です。修正前に、大規模テナント相当のデータセットでテスト環境の OOM を再現しました。修正後に同じデータでカスケードを再度発生させると、Pod のメモリは横ばいのままで、ピークは「200人とその直属の上位」だけで決まり、ネットワークの規模には左右されませんでした。リリース後、このコンシューマーで OOM は二度と起きていません。

## 修正後に残ったもの

OOM は解消しましたが、根本的な問題が二つ残りました。同じ系統上の変更同士がまったく調整されていないこと、そして1件の Kafka メッセージ、1つの handler でサブツリー全体を同期的に処理しなければならないことです。

なかでも私が一番気にしていたのは、**同じ系統への同時変更**です。A → B → C というネットワークを考えます。

- 管理者1が A を 12% から 5% に変更する。
- 同時に、管理者2が B を 8% に変更する。管理者2の検証は A の古い値 12% を読むので、通ってしまう。
- 管理者1のカスケードが先に B を 5% に切り詰め、その後に管理者2の書き込みで B = 8% になる。

結果として B > A となり、両方とも成功を返し、不変条件が破られます。順序の入れ替わった消費は、この特殊なケースにすぎません。

ほかの問題も同じ構造から生じています。

- **1件のメッセージの処理が長い**。ローリングデプロイでリバランスが起きると、長い handler がタイムアウトしてコンシューマーグループから外され、別のインスタンスがメッセージを最初からやり直すことがあります。
- **失敗の粒度が粗すぎる**。途中のバッチが失敗しても、エラーが最後まで返されません（この部分は元のコードを引き継いだものです）。そのため「一部は適用済みなのに、リトライされない」状態になり得ますし、進捗も見えません。
- **流量制限がインスタンス単位でしか効かない**。200 / 50 ms は各コンシューマー内の固定値なので、複数のインスタンスが同時にカスケードを処理すると、データベースへの負荷が積み重なります。

## もう一度やるなら：コマンドはワークフローで、イベントは Kafka で

これは OOM を直した後に考えた案で、退職までに実装はしていません。あくまで設計です。

カスケードは実は**コマンド**であって、イベントではありません。呼び出し側は結果を知る必要があり、同時変更を防ぐ必要があり、バッチ単位でリトライする必要があります。そこで、管理画面の API から直接 Temporal の workflow を起動し、新しい設定を入力として渡します。workflow はまずそのノード自身の設定を書き込み、次に階層ごと・バッチごとに下へカスケードし、1バッチにつき1つの activity とします。すべて終わったら「設定変更済み」のイベントを発行し、監査やキャッシュなどの下流がそれぞれ購読します。

同じ系統への変更は「ブランチロック」で直列化します。ロックの範囲は対象ノードのすべての祖先とすべての子孫です。サブツリーが重なり得るのはこれらのノードだけなので、兄弟の枝は並行して動けます。カスケードの処理中は、同じ系統への2回目の変更はそのまま拒否します。頻度の低い管理操作なので、「待ってからやり直す」コストは許容できます。

これで上の問題にはそれぞれ答えが出ます。同じ系統では同時に1つのカスケードしか動かないので、競合や順序の入れ替わりの前提がなくなります。1バッチ1 activity なので、失敗してもそのバッチだけをリトライでき、進捗は UI で確認できます。流量制限は task queue でまとめて設定し、インスタンスごとに sleep する必要がなくなります。代わりに、Temporal クラスターへの依存と、workflow コードが守るべき決定性の制約が加わります。

## 得たこと

**どこを本当に順番に処理しなければならないかを先に決め、それ以外はバッチに分ける**。今回の OOM は、正しさのために問題全体を「すべてを一度に見なければならない」ものとして扱ったことから始まりました。本当に必要だったのは「階層間の順序」だけでした。依存関係を図にしてからは、メモリは「データ量とともに増える」ものから「バッチサイズだけで決まる」ものに変わり、上限を計算できるようになりました。

もう一つはもっと素朴なことです。ロジックを正しく直しても、それで終わりではありません。テナントの規模に応じて処理量が増えるコードは、リリース前に最大規模のテナントのデータで一度動かしておくべきです。
