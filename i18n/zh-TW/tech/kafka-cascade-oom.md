這次 OOM 是我自己引入的。邏輯改對了，但我沒有用大型網路的資料驗證。上線後，大租戶的頂層合作夥伴一改設定，連鎖更新消費者的 Pod 記憶體就被吃滿、被砍掉、重啟，然後再一次吃滿。

這篇記下它是怎麼發生的、怎麼修的，以及修完以後還剩下什麼問題。

## 背景：一棵要維持不變式的樹

平台上的合作夥伴網路是一棵樹，一般模式最多 10 層。每個節點有依產品類別細分的分潤規則，以及依幣別的交易限額。

系統要維持一個不變式：**下級的值不能超過直屬上級**。上級修改設定後，服務會發出一則連鎖事件，由一個 Kafka 消費者把整個下線重新截斷一遍。

這個消費者的第一版是同事寫的。它分批處理，但每個下級都和「被修改的那個人」比較。後來需求改成**依各自直屬上級的新值截斷**，這部分由我來改。為了拿到每個下級的直屬上級的新值，我把原本每批 200 個的迴圈，改成一次載入全部下線及其上級的設定。

邏輯是對的，記憶體卻沒有上界。

## 現象：一則訊息卡死一個分割區

上線後我一直盯著這個消費者：

- 大租戶的頂層合作夥伴一改規則，消費者的 Pod 記憶體就被吃滿，被 OOMKill 後重啟；
- 被砍時這則訊息的 offset 還沒提交，重啟後它會被重新投遞，於是再次 OOM，Pod 進入重啟循環；
- 同一分割區後面的事件全部被堵住；
- 小租戶上一切正常。

最後一點很關鍵：只在大型網路上出問題，代表問題和資料規模有關，而不是邏輯錯了。

## 定位：一段和網路規模成正比的載入

1. **縮小範圍**。只在連鎖事件上出現，只在大型網路上出現，時間上緊跟在我的那次改動之後。
2. **估算記憶體**。設定列數 = 下線人數 × 產品類別數 × 類型數，每列還帶一個依幣別的 JSON。一次載入，等於把整棵子樹的設定都反序列化進記憶體。記憶體隨網路規模線性成長，沒有上界。
3. **確認**。對照 diff，唯一的結構性變化就是把「分批」改成了「全量」。

## 修法：先找相依性，再分批

我當初改成全量載入，是因為擔心分批會破壞正確性：下級要和直屬上級的**新**值比較，如果先算下層，讀到的就是上級的舊值。

但把相依關係畫出來，問題就清楚了：**層與層之間有相依，同一層內部沒有**。所以只有層與層之間需要循序執行，層內可以隨意分批。

```text
上級 P 修改設定 → 寫入資料庫 → 發出連鎖事件 {舊值, 新值, 選項}
                                │
[連鎖更新消費者]  失敗 → 獨立的 retry topic（有限次數，間隔遞增）→ 死信
  1. 查出 P 的全部下線（只取 id 和層級）
  2. 依層級分組，由上往下逐層處理：
       每層切成每批 200 個
         → 只載入這一批人的直屬上級的（新）設定
         → 每個下級依直屬上級的新值截斷 → 寫入資料庫
         → 批次之間暫停 50 ms
  3. 清除受影響使用者的快取
```

核心迴圈大致如下（示意程式碼，不是原始程式碼）：

```go
for depth := 1; depth <= maxDepth; depth++ { // 層間循序：上一層寫完，下一層才讀得到新值
	ids := idsByDepth[depth]
	for start := 0; start < len(ids); start += batchSize {
		batch := ids[start:min(start+batchSize, len(ids))]

		// 只載入這一批人的直屬上級，記憶體只和 batchSize 有關
		parents, err := store.LoadParentSettings(ctx, batch)
		if err != nil {
			return err
		}
		updated := clampToParents(batch, parents) // 下級不能超過直屬上級
		if err := store.SaveSettings(ctx, updated); err != nil {
			return err
		}
		time.Sleep(pause) // 背景任務，把資料庫讓給線上請求
	}
}
```

幾個取捨：

| 選擇 | 理由 | 沒採用的方案 |
|---|---|---|
| 依層由上而下 | 層間有相依，層內沒有 | 整棵樹拓撲排序後放進記憶體，這正是 OOM 的做法 |
| 每批只載入直屬上級 | 層很寬時，整層上級本身也很大 | 載入整層上級（我的第一版修復就是這樣，後來又縮小了一次） |
| 批內循序，批次之間暫停 50 ms | 連鎖更新是背景任務，沒有即時性要求 | 層內並行，會成倍放大對 MySQL 的壓力 |
| 規則留在 Go 裡 | 截斷涉及依幣別的 JSON 和多種類型 | 用遞迴 CTE 一條 SQL 算完，表達不了這些規則 |

修復分兩步上線：先依層分批，OOM 就此解決；之後再把「讀整層上級」縮小到「只讀這一批的直屬上級」。

驗證方式：修復前，我在測試環境用大租戶規模的資料集重現了 OOM；修復後，用同一份資料重新觸發連鎖更新，Pod 記憶體保持平穩，峰值只取決於「200 人加上他們的直屬上級」，和網路規模無關。上線後，這個消費者沒有再發生過 OOM。

## 修完以後還剩什麼

OOM 解決了，但根源上還有兩個問題：同一條線上的修改之間沒有任何協調；一則 Kafka 訊息、一個 handler，要同步處理整棵子樹。

其中我最在意的是**同一條線上的並行修改**。假設網路 A → B → C：

- 管理員甲把 A 從 12% 改成 5%；
- 管理員乙同時把 B 改成 8%。乙的驗證讀到的是 A 的舊值 12%，於是通過；
- 甲的連鎖更新先把 B 截成 5%，隨後乙寫入 B = 8%。

最終 B > A，兩邊都回傳成功，不變式被破壞。亂序消費只是它的一個特例。

其他問題也來自同一個結構：

- **一則訊息跑很久**。滾動部署觸發 rebalance 時，長 handler 可能逾時被踢出消費者群組，訊息由另一個執行個體從頭再跑一遍；
- **失敗粒度太粗**。中間某一批失敗時，錯誤沒有一路往上回傳（這一段沿用了原本的程式碼），可能出現「部分已套用、卻不重試」的狀態，進度也看不到；
- **限流只在單一執行個體內有效**。200 / 50 ms 是每個消費者自己的固定值，多個執行個體同時跑連鎖更新時，資料庫的壓力會疊加。

## 如果重來：命令走工作流程，事件走 Kafka

這是我修完 OOM 後想到的方案，離職前沒有落地，所以只算設計。

連鎖更新其實是一個**命令**，不是事件：呼叫方需要知道結果，需要防止並行修改，需要按批重試。所以我會讓後台 API 直接啟動一個 Temporal workflow，把新設定當作輸入。workflow 先寫入這個節點自己的設定，再依層、依批往下連鎖更新，每批一個 activity；全部完成後，再發出一則「設定已變更」的事件，讓稽核、快取這些下游各自訂閱。

同一條線上的修改，用一把「分支鎖」循序化。鎖的範圍是目標節點的所有祖先加上所有後代，只有這些節點的子樹會和它重疊，兄弟分支可以照常並行。連鎖更新進行中時，同一條線上的第二次修改直接被拒絕；這是低頻的後台操作，「排隊重試」的代價可以接受。

這樣上面幾個問題都有了解法：同一條線同一時間只有一個連鎖更新在跑，競爭和亂序的前提都沒了；每批一個 activity，失敗只重試那一批，進度在 UI 裡看得到；限流交給 task queue 統一設定，不再是每個執行個體各自 sleep。代價是多了對 Temporal 叢集的相依，以及 workflow 程式碼要遵守的確定性限制。

## 我帶走的東西

**先確定哪裡必須循序執行，再在其餘地方分批**。這次的 OOM，起因是我為了正確性，把整個問題當成「必須全部看見」的問題；真正需要的只是「層與層之間的順序」。把相依關係畫出來以後，記憶體從「隨資料規模成長」變成「只取決於批次大小」，上界是可以算出來的。

另一件事更樸素：邏輯改對了不等於改完了。凡是處理量隨租戶規模成長的程式碼，上線前都應該用最大租戶規模的資料跑一遍。
