这次 OOM 是我自己引入的。逻辑改对了，但我没有用大网络的数据验证。上线后，大租户的顶层合作伙伴一改设置，级联消费者的 Pod 内存就打满、被杀、重启，然后再一次打满。

这篇记下它是怎么发生的、怎么修的，以及修完以后还剩下什么问题。

## 背景：一棵要维持不变式的树

平台上的合作伙伴网络是一棵树，常规模式最多 10 级。每个节点有按产品类目细分的分成规则，以及按币种的交易限额。

系统要维持一个不变式：**下级的值不能超过直属上级**。上级修改设置后，服务会发出一条级联事件，由一个 Kafka 消费者把整个下线重新截断一遍。

这个消费者的初版是同事写的。它分批处理，但每个下级都和"被修改的那个人"比较。后来需求改成**按各自直属上级的新值截断**，这部分由我来改。为了拿到每个下级的直属上级的新值，我把原来每批 200 个的循环，改成了一次性加载全部下线及其上级的设置。

逻辑是对的，内存却没有上界。

## 现象：一条消息卡死一个分区

上线后我一直盯着这个消费者：

- 大租户的顶层合作伙伴一改规则，消费者的 Pod 内存就打满，被 OOMKill 后重启；
- 被杀时这条消息的 offset 还没提交，重启后它会被重新投递，于是再次 OOM，Pod 进入重启循环；
- 同一分区后面的事件全部被堵住；
- 小租户上一切正常。

最后一条很关键：只在大网络上出问题，说明问题和数据规模有关，而不是逻辑错了。

## 定位：一段和网络规模成正比的加载

1. **缩小范围**。只在级联事件上出现，只在大网络上出现，时间上紧跟我的那次改动。
2. **估算内存**。设置行数 = 下线人数 × 产品类目数 × 类型数，每行还带一个按币种的 JSON。一次性加载，等于把整棵子树的设置都反序列化进内存。内存随网络规模线性增长，没有上界。
3. **确认**。对照 diff，唯一的结构性变化就是把"分批"改成了"全量"。

## 修法：先找依赖，再切批

我当初改成全量加载，是因为担心分批会破坏正确性：下级要和直属上级的**新**值比较，如果先算下层，读到的就是上级的旧值。

但把依赖关系画出来，问题就清楚了：**层与层之间有依赖，同一层内部没有**。所以只有层与层之间需要串行，层内可以随意切批。

```text
上级 P 修改设置 → 写库 → 发级联事件 {旧值, 新值, 选项}
                                │
[级联消费者]  失败 → 独立的 retry topic（有限次数，间隔递增）→ 死信
  1. 查出 P 的全部下线（只取 id 和层级）
  2. 按层级分组，从上往下逐层处理：
       每层切成 200 个一批
         → 只加载这一批人的直属上级的（新）设置
         → 每个下级按直属上级的新值截断 → 写库
         → 批与批之间停 50 ms
  3. 删除受影响用户的缓存
```

核心循环大致是这样（示意代码，不是原代码）：

```go
for depth := 1; depth <= maxDepth; depth++ { // 层间串行：上一层写完，下一层才读得到新值
	ids := idsByDepth[depth]
	for start := 0; start < len(ids); start += batchSize {
		batch := ids[start:min(start+batchSize, len(ids))]

		// 只加载这一批人的直属上级，内存只和 batchSize 有关
		parents, err := store.LoadParentSettings(ctx, batch)
		if err != nil {
			return err
		}
		updated := clampToParents(batch, parents) // 下级不能超过直属上级
		if err := store.SaveSettings(ctx, updated); err != nil {
			return err
		}
		time.Sleep(pause) // 后台任务，把数据库让给在线请求
	}
}
```

几个取舍：

| 选择 | 理由 | 没选的方案 |
|---|---|---|
| 按层自上而下 | 层间有依赖，层内没有 | 整棵树拓扑排序后放进内存，这正是 OOM 的做法 |
| 每批只加载直属上级 | 层很宽时，整层上级本身也很大 | 加载整层上级（我的第一版修复就是这样，后来又收窄了一次） |
| 批内串行，批间停 50 ms | 级联是后台任务，没有实时性要求 | 层内并发，会成倍放大对 MySQL 的压力 |
| 规则留在 Go 里 | 截断涉及按币种的 JSON 和多种类型 | 用递归 CTE 一条 SQL 算完，表达不了这些规则 |

修复分两步上线：先按层分批，OOM 就此解决；之后再把"读整层上级"收窄到"只读这一批的直属上级"。

验证方式：修复前，我在测试环境用大租户规模的数据集复现了 OOM；修复后，用同一份数据重新触发级联，Pod 内存保持平稳，峰值只取决于"200 人加上他们的直属上级"，和网络规模无关。上线后，这个消费者没有再出现过 OOM。

## 修完以后还剩什么

OOM 解决了，但根源上还有两个问题：同一条线上的修改之间没有任何协调；一条 Kafka 消息、一个 handler，要同步处理整棵子树。

其中我最在意的是**并发修改同一条线**。设想网络 A → B → C：

- 管理员甲把 A 从 12% 改成 5%；
- 管理员乙同时把 B 改成 8%。乙的校验读到的是 A 的旧值 12%，于是通过；
- 甲的级联先把 B 截成 5%，随后乙写入 B = 8%。

最终 B > A，两边都返回成功，不变式被破坏。乱序消费只是它的一个特例。

其他问题也来自同一个结构：

- **一条消息跑很久**。滚动发布触发 rebalance 时，长 handler 可能超时被踢出消费组，消息由另一个实例从头再跑一遍；
- **失败粒度太粗**。中间某一批失败时，错误没有一路返回（这一段沿用了原来的代码），可能出现"部分已应用、却不重试"的状态，进度也看不到；
- **限速只在单个实例内有效**。200 / 50 ms 是每个消费者自己的固定值，多个实例同时跑级联时，数据库的压力会叠加。

## 如果重来：命令走工作流，事件走 Kafka

这是我修完 OOM 后想到的方案，离职前没有落地，所以只算设计。

级联其实是一个**命令**，不是事件：调用方需要知道结果，需要防并发，需要按批重试。所以我会让后台 API 直接启动一个 Temporal workflow，把新设置作为输入。workflow 先写这个节点自己的设置，再按层、按批往下级联，每批一个 activity；全部完成后，再发一条"设置已变更"的事件，给审计、缓存这些下游各自订阅。

同一条线上的修改，用一把"分支锁"串行化。锁的范围是目标节点的所有祖先加上所有后代，只有这些节点的子树会和它重叠，兄弟分支可以照常并行。级联在处理中时，同一条线上的第二次修改直接被拒绝；这是低频的后台操作，"排队重试"的代价可以接受。

这样上面几个问题都有了着落：同一条线同一时刻只有一个级联在跑，竞争和乱序的前提都没了；每批一个 activity，失败只重试那一批，进度在 UI 里看得见；限速交给 task queue 统一配置，不再是每个实例各自 sleep。代价是多了对 Temporal 集群的依赖，以及 workflow 代码要遵守的确定性约束。

## 我带走的东西

**先确定哪里必须串行，再在其余地方切批**。这次的 OOM，起因是我为了正确性把整个问题当成"必须全部看见"的问题；真正需要的只是"层与层之间的顺序"。把依赖关系画出来以后，内存从"随数据规模增长"变成了"只取决于批大小"，上界是可以算出来的。

另一件事更朴素：逻辑改对了不等于改完了。凡是处理量随租户规模增长的代码，上线前都应该用最大租户规模的数据跑一遍。
